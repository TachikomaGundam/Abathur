# 沙箱分层：把「部署」和「防自改」拆开（2026-10-30）

## 问题（机主逐字质疑）

> 「需要我跑的命令，是否意味着在别人安装了阿巴瑟以后也要跑？这是否符合单行安装、自动化运行原则？」

现状：沙箱靠一条 `sudo bash scripts/install-sandbox.sh --apply` 部署。对别人的安装来说这是第二条命令、且要 root —— 违背单行安装与自动化原则。

## 根因

我把两件事绑成了一个 root 安装：
1. **部署**（把沙箱代码放到机器上）；
2. **防自改**（沙箱工件属主 root，使被沙箱的进程无法改写自己的牢笼）。

这两件事的代价完全不同：前者本应免费，后者必须 root。

## 机器事实（2026-10-30 实测）

| 项 | 值 |
|---|---|
| 沙箱执行器（仓库） | `scripts/sandbox-exec` sha256 `1a84eae3…`（v13：/var/tmp 缺失回退 + MCP 目录条件只读挂载） |
| 装机版 | `/usr/local/lib/abathur/sandbox-exec` sha256 `50c466a5…`（v11，root:root 0755） |
| 启动器 | `/usr/local/lib/abathur/launcher`（root:root，已入仓） |
| 插件钩子 | `~/.config/opencode/plugins/sandbox-bash.js` 拦截 `tool.execute.before` 的 bash，转调沙箱执行器 |
| bwrap | 0.11.1，非特权用户可运行（实测断网 rc=6、env 12 项、PID 命名空间独立） |
| 嵌套 | 沙箱内再跑 bwrap 失败（`ENOSPC` 命名空间深度）——不影响生产（插件在宿主进程执行） |
| 断网副作用 | 沙箱内无法访问本机模型端点（127.0.0.1:8010/8000 rc=7） |

## 方案：两层沙箱

### Tier 1（默认，零 root，随插件走）

插件自己调 `bwrap`，不依赖任何 root 工件：
- bwrap 路径解析：`command -v bwrap` → `/usr/bin/bwrap` → 不存在则降级（见下）
- 策略内置于插件包：`sandbox-policy.json`（工作区、只读挂载表、断网、ulimit、遮蔽路径）
- 家目录只放行工作区；`/var/tmp` 用命名空间内 tmpfs
- 安装 = 安装插件本身，**没有第二条命令**

### Tier 2（本机加固，一次 root，仅高价值主机）

保留现状：root 属主启动器 + 字节钉定 + `/etc/abathur` 配置。用于「密钥、浏览器、会话库同机」的主机。

### 选择逻辑

```
if (存在 root 属主且非本用户可写的 /usr/local/lib/abathur/sandbox-exec)
    用 Tier 2
else if (bwrap 可用)
    用 Tier 1
else
    降级：仅工具层路径策略，并在首次 bash 调用输出一行显式告警
```

### 告警文本（降级时）

```
[sandbox] 未找到 bwrap：本次仅应用路径策略，命令以本用户全权执行。
          安装 bubblewrap 可获得系统级沙箱。
```

## 为什么这样分层是对的

| 需求 | Tier 1 | Tier 2 |
|---|---|---|
| 别人装完即可用 | ✅ 零命令 | ❌ 要 sudo |
| 防误操作 / 防注入 | ✅ | ✅ |
| 防被沙箱进程改写自身牢笼 | ❌（同 uid 可改插件） | ✅（root 属主 + 字节钉定） |
| 可随 npm 包分发 | ✅ | ❌ 机器绑定 |

**诚实声明**：Tier 1 是软墙。它挡住「我随手 rm 了不该 rm 的」和「网页注入让我执行恶意命令」，挡不住「一个铁了心重写自己插件配置的进程」。后者只有 Tier 2 或账户分离能挡。

## 兼容与迁移

1. 插件改为：先探测 Tier 2 工件，存在则调用它（保持本机现状不变）；否则内置 Tier 1。
2. `install-sandbox.sh` 改为 `--hardened`，仅在 `--hardened --apply` 时执行；默认打印说明并退出 0，不作为安装步骤。
3. 文档写明两种强度；不写「已隔离」而写「沙箱强度：硬/软」。

## 验收（必须是机器判据）

| # | 判据 | 命令/观测量 |
|---|---|---|
| V1 | Tier 1 生效 | 无 root 工件时，bash 内 `curl` 失败、`env` ≤ 12 项、`ls /home/lab` 仅工作区 |
| V2 | Tier 2 优先 | 存在 root 工件时，实际执行的是 root 版字节（strace/日志或 banner） |
| V3 | 无 bwrap 降级 | 移除 PATH 中的 bwrap → 命令仍执行 + 告警一行 + 退出码不变 |
| V4 | 策略一致 | 同一命令在两层下对敏感路径（`.ssh`、`docker.sock`、`/dev/input`）都不可达 |
| V5 | 不破坏工作 | `npm test`（本仓）在两层下行为一致；工作区读写正常 |
| V6 | 跨平台显式 | macOS 上不假装有沙箱：输出「本平台仅路径策略」并继续 |

## 未决（请评审席重点攻击）

1. 选择逻辑里「存在 root 工件就用 Tier 2」会不会让**恶意方**通过放置一个假工件劫持路径？（插件调用的是绝对路径，但若该路径可被用户写则等同无墙）
2. Tier 1 的策略文件放在插件包内，升级插件会不会静默改策略？如何让用户看见变更？
3. 降级告警只出现一行，是否足够？是否应默认拒绝执行而非降级执行？
4. 断网导致本机模型端点不可达——Tier 1 是否应允许 localhost 白名单？若允许，如何防内网横向？
5. macOS/Windows 是否需要给出替代机制（seatbelt / AppContainer），还是明确标注不支持？
