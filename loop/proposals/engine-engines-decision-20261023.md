# 0.4.1 engines 声明决策记录（v2 — 更正稿，2026-10-23）

## 更正声明

v1 草案声称「0.3.0 → 0.4.1 engines 有非空集合差」「Node 24 短期支持已 EOL」。两条均错误：

1. **集合差不存在**：v0.3.0 engines = `^22.22.2 || ^24.15.0 || >=26.0.0`；0.4.1 恢复后 engines = 同一字符串。git diff 可证，无差异。
2. **Node 24 不是 EOL**：Node 24「Krypton」是活跃 LTS，维护至 2028-04-30（实测：nodesjs.org download release API + 搜索引擎结果一致）。EOL 的是 23.x（奇数版本短期支持，2025-06 已 EOL）。

错误根因：我从「0.4.0 把 engines 放宽到 >=22」这个事实出发，误以为 0.4.1 恢复严格面后与 0.3.0 有差异。实际上恢复的是**同一个字符串**，差异只在 0.4.0 与 0.3.0/0.4.1 之间。

## 实际决策

engines = `>=22.22.1`。理由链（法院 d2a1 约束：下限以已实测最低运行时为唯一依据）：
- SDK 已移出必经安装路径（peer-optional），ini@7.0.0 的约束不再适用于安装者——0.3.0 字符串的存在理由（迁就 ini）已消失。
- 已实测最低运行时 = 本机 node v22.22.1（全量测试 394 项在此版本绿）。下限取实测值，不多不少。
- 不设上限排除：23/25/24.x 未实测——声明 `>=22.22.1` 表示「下限实测、更高版本按 Node 兼容性惯例预期可用」，非严格模式下 npm 对任何版本只警告不拦截；这比照搬含 ini 痕迹的旧字符串更诚实。
- 不照搬 0.3.0 字符串的另一原因：它会把本机 22.22.1 排除在声明面之外（自己开发机都不合规，荒谬）。

## 被法院驳回后学到的

- 三席一致指出 v1 把「0.4.0 引回的旧范围」当成了「0.4.1 新收紧」——提交锚没看清 0.4.0 才是变更点。
- 提交前必须 diff 目标字段的两个版本，不能凭印象假设有差异。
- 「Node 24 EOL」是事实错误，web 搜索 30 秒就能证伪——草案里写理由前应先查。
