# MCP 面残余：三档处置方案待裁（2026-10-30）

## 问题事实（机器可核）

- 本机的 MCP 服务 `codegraph`、`context7`、`websearch` 由第三方插件 **oh-my-openagent** 在 **opencode 宿主进程内**拉起，实现在该插件包内 `dist/mcp/*.js`（不是我仓的配置项，也不是 stdio 子进程登记表里的条目）。
- 因此两条已建闸都管不到它：
  - bash 沙箱（`Abathur/.opencode/plugins/sandbox-bash.js`）只包 `bash` 工具的命令行；
  - 文件工具策略只包 `read/write/edit/grep/glob`。
- MCP 工具被调用时代码在宿主进程执行：**有网络、能读整棵家目录、能以 lab 身份写任何地方**。它是我（以及任何一条产线的座席）唯一还在无约束执行的通道。
- 已交付器具：`/home/lab/workspace/harness/Abathur/scripts/check-mcp-integrity.sh`（对 `dist/mcp/*.js` 做字节基线对账，需人类跑一次 `--update` 建基线）。
- 具名残余编号：**R-D24**。

## 三档方案

| 档 | 做法 | 得到什么 | 代价 |
|---|---|---|---|
| **A 字节对账** | 人类建基线，之后定期/变更前对账，字节变了就报警并停用语义 | 不改功能；篡改与插件自动升级可见 | 只**发现**不**拦阻**；MCP 正常功能本身仍全权 |
| **B 减面** | 在配置里禁用风险最高的 MCP（`websearch` 出网、`codegraph` 读全树），保留其余 | 真减少可达面 | 损失我用得上的能力（我确实常用 websearch/context7/codegraph 检索） |
| **C 补第三方隔离器** | 引入外部「MCP 沙箱代理」类插件把 MCP 子进程包起来 | 结构上把 MCP 关进沙箱 | 又引入一个第三方代码面进宿主进程；与「减少宿主面」方向相反 |

## 需要被追问的角度（请评审席主动覆盖）

1. 三档是不是穷尽？有没有第四种（例如：把 MCP 需要的能力降级为经 bash 沙箱调用的 CLI；或在插件钩子里对 MCP 工具调用做参数白名单/域名白名单）。
2. 「宿主进程内的第三方插件」这一整类（不止 MCP）该如何治理？插件钩子本身也是宿主代码。
3. A 档的对账基线由谁持、放哪里才算单源且不自我背书（我自己写的基线，我自己能改=无墙）。
4. 若选 B：具体禁哪几个，按什么判据排序（出网能力 / 全树读 / 写能力），并给出**禁用后我还能不能完成考场与工程任务**的可核推论。
5. 与「多产线共面」的关系：MCP 是用户级共享面，禁用会影响其他产线的座席——单点决定的爆炸半径如何声明。

## 约束（机主已定，不得违反）

- 不建多个 Unix 账户；不常驻 root 落脚点；座席机制不得装到用户级共享配置（事故已定此铁律）。
- 机制须能随插件包分发；机主要能直接看到座席的全部工作文件与会话库。
- 座席不得把可自行动作转嫁机主代跑；需要人类持键的动作必须写清「为什么座席不能做」。
