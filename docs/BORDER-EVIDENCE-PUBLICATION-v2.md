## 2. 为什么不是「脱敏后照发」

1. 路径脱敏会让已封包的 `sha256` 全部失效——而 `sha256` 是这些证据唯一的核对手段。
2. 剩下的 586 条非路径类（会话工件 382、内网地址 126、SSH 目标 15、密钥 32）不会因为改路径而消失。
3. 内容清洗（把命中串替换成占位符）会让证据不再是被判卷的那份字节——证据一旦变形就不再是证据。

## 3. 推荐方案（唯一方案，不是菜单）

**三道分离**：

1. **公开仓**：代码 + `docs/evidence-manifests/<GEN>.sha256`（清单只含 repo-relative 路径与哈希，不含内容）。清单本身不含路径外的秘密，能过闸。
2. **内部仓**：证据本体（`evidence/` 镜像按现有 `publish-evidence.py` 产出）。
3. **本地归档**：`loop-archive/`（现状不变，不入任何远端）。

**为什么清单够用**：第三方要复算，需要的是「哪份字节、在哪个提交」——这两项清单都给了；需要字节本身时，走内部仓或本地归档。这不满足 v1 里我写的「陌生人只凭公开面复算」那条约束，所以我把它升级为需要机主裁定的政策变更，而不是悄悄放宽。

## 4. 必须由机主改的约束（我不能自裁）

v1 第 4 条写的是：公开发布必须让第三方**只凭公开面**复算。按上面实测，这条与「证据不变形」互斥。两个选项，必须机主选：

- **4A**：放宽为「公开面给清单，字节走内部仓」，即本方案；
- **4B**：要求公开面可独立复算，则必须接受证据脱敏后权重下降（哈希不再对得上原封包）。

我不替机主选。

## 5. 上推策略（另一个必须机主定的点）

公开面已分叉（10-06 之后 300 本地提交）。三条路：

- **P1 不推**：公开面冻结在当前，最安全，但公开仓陈旧；
- **P2 强推**：需机主按键，且会让远端 62 个提交不可达（历史改写）；
- **P3 新建公开仓**：旧仓归档，新仓从干净的隔离 checkout 起，本地证据不入。

我推荐 **P3**：不改写既有历史、不丢远端提交、公开面从干净点重新开始。
